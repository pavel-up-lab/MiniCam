# План диагностики скачков архивного видео на Apple Silicon

## Принцип выполнения

Работа ведётся в `fix/apple-silicon-archive`. На первом цикле добавляется только наблюдаемость и один изолированный профиль `foreground-only`. Параметры транспорта, декодера и поздних кадров не меняются до анализа baseline. Каждый следующий эксперимент добавляется отдельным коммитом и только когда предыдущий результат требует его по дереву решений.

## Этап 1. Добавить проверяемое ядро диагностики

Файлы:

- создать `MiniCam/Playback/PlaybackDiagnostics.swift`;
- создать `MiniCamTests/PlaybackDiagnosticsTests.swift`.

Шаги:

1. Сначала добавить падающие тесты для очистки:
   - RTSP URL с `user:password@host`;
   - отдельно встречающихся имени пользователя и пароля;
   - параметров `Authorization`, `rtsp-user` и `rtsp-pwd`;
   - безопасного сообщения без секретов, которое не должно изменяться.
2. Добавить тесты реестра владельцев `main`, `frameCache` и `archiveSampler`: открытие, запрос остановки, освобождение, повторное освобождение и максимальное одновременное число.
3. Добавить тест определения обратного хода времени с небольшим допуском на одинаковые callback и сбросом при новом transition ID.
4. Реализовать небольшие типы без зависимости от VLCKit:
   - `PlaybackDiagnosticRedactor`;
   - `RTSPSessionRegistry`;
   - `PlaybackTimeDiscontinuityDetector`;
   - структурированное событие с категорией, временем, transition/player ID и безопасными полями.
5. Убедиться, что ни один тип события не принимает `CameraCredentials` или полный URL как сохраняемое поле. Учётные данные передаются redactor только для фильтрации и не удерживаются дольше активного подключения.

Проверка:

```sh
xcodebuild -workspace MiniCam.xcworkspace -scheme MiniCam -configuration Debug -derivedDataPath build-test-archive-diagnostics test
```

## Этап 2. Добавить Debug-only sink и журнал VLCKit

Файлы:

- расширить `MiniCam/Playback/PlaybackDiagnostics.swift`;
- создать `MiniCam/Playback/VLCPlaybackDiagnosticLogger.swift`;
- дополнить `MiniCamTests/PlaybackDiagnosticsTests.swift`.

Шаги:

1. Реализовать ограниченный диагностический файл в `FileManager.default.temporaryDirectory`; при каждом запуске файл заменяется, а не дописывается.
2. Перед любой записью применять redactor. При ошибке записи отключать только файловый sink, не воспроизведение.
3. Подключить собственный объект `VLCLogging` к общей `VLCLibrary.sharedLibrary().loggers` только под `#if DEBUG`.
4. Категоризировать сообщения по модулю и ключевым признакам: RTSP-команды и коды, decoder/VideoToolbox, discontinuity, PTS/DTS, поздние кадры и RTP. Не удалять неизвестное сообщение после очистки; сохранять его как `unclassified`.
5. Не утверждать соответствие глобального сообщения VLC конкретному плееру, если `VLCLogContext.objectId` нельзя надёжно связать с экземпляром `VLCMediaPlayer`. Использовать временную корреляцию и помечать источник как `library`.
6. Добавить тест, что неизвестное сообщение проходит в sink только после очистки, а сбой sink не выбрасывается в вызывающий код.

Проверка:

- тесты диагностики;
- поиск в исходниках на прямой `print` диагностических URL и credentials;
- Debug-сборка;
- Release-сборка, в которой нет активной регистрации диагностического logger.

## Этап 3. Инструментировать основной плеер без изменения политики

Файлы:

- изменить `MiniCam/Playback/VLCPlaybackController.swift`;
- при необходимости дополнить `MiniCamTests/PlaybackDiagnosticsTests.swift`.

Шаги:

1. Передать в контроллер Debug-only diagnostics dependency с no-op значением по умолчанию.
2. При `playLive` и `playArchive` записывать только вид потока, транспорт, transition ID и обезличенный player ID.
3. Разнести события `stop requested`, `state stopped`, `player detached`, `player replaced`, `play requested`, `playing`, `ended` и `error`.
4. В `mediaPlayerTimeChanged` передавать миллисекунды в `PlaybackTimeDiscontinuityDetector`. При новом переходе сбрасывать detector.
5. Заменить диагностическое понимание «первого кадра»: существующий `frameRevision` пока не менять, чтобы не затронуть UI, но отдельно запустить короткий Debug-only probe `videoView.hasVideo`. Записать время первого `true` или тайм-аут, не меняя состояние плеера.
6. Записывать фактическую конфигурацию live/archive без URL и без значений credentials.
7. Не менять `--no-drop-late-frames`, `--no-skip-frames`, cache, transport или VideoToolbox на этом этапе.

Проверка:

- тесты чистых диагностических типов;
- Debug-сборка;
- ручной запуск эфира с проверкой, что diagnostics не влияет на изображение и управление.

## Этап 4. Инструментировать фоновые источники

Файлы:

- изменить `MiniCam/Playback/FrameCacheRecorder.swift`;
- изменить `MiniCam/Playback/ArchiveFrameSampler.swift`;
- изменить `MiniCam/Detection/ArchiveMotionAnalyzer.swift`;
- изменить `MiniCam/App/AppContainer.swift`.

Шаги:

1. Передать один общий diagnostics/session registry из `AppContainer` всем трём владельцам.
2. Для `FrameCacheRecorder` различать HTTP-режим и момент фактического перехода в RTSP fallback. HTTP-запрос не увеличивает счётчик RTSP.
3. Для `ArchiveFrameSampler` фиксировать начало, отмену, завершение и ошибку каждого RTSP-сеанса.
4. При `suspendSampling` отдельно записывать отмену sampler; при `resumeSampling` — разрешение нового запуска, а не открытый сеанс.
5. Для основного плеера закрывать запись реестра только после detach/replace или окончательной остановки, а не сразу при вызове `stop()`.
6. Сверить реестр с сетевыми соединениями процесса в ручном запуске. Расхождение занести в отчёт, не компенсировать предположением.

Проверка:

- тесты реестра;
- сценарий connect → live → archive → seek → live;
- в логе ни в один момент не должно быть отрицательного счётчика или освобождения неизвестного идентификатора без отдельного диагностического предупреждения.

## Этап 5. Добавить первый изолированный эксперимент

Файлы:

- создать `MiniCam/Playback/ArchivePlaybackExperiment.swift`;
- создать `MiniCamTests/ArchivePlaybackExperimentTests.swift`;
- изменить `MiniCam/App/AppContainer.swift`.

Шаги:

1. Добавить падающие тесты разбора Debug launch argument для `baseline` и `foreground-only`, неизвестного значения и конфликтующих значений.
2. Реализовать Debug-only выбор профиля. В Release результат всегда `baseline` независимо от process arguments.
3. В `foreground-only` после подключения не запускать `FrameCacheRecorder` и `ArchiveMotionAnalyzer`. Это оставляет один основной RTSP-плеер на весь опыт и не требует менять переходы основного воспроизведения.
4. Не добавлять пока `software-decoding`, transport и frame-policy в исполняемую логику; их названия остаются зарезервированы спецификацией, но реализуются только при достижении соответствующего шага дерева решений.
5. В стартовом событии записать выбранный профиль.

Проверка:

- тесты выбора профиля;
- baseline сохраняет текущий запуск кеша и анализатора;
- `foreground-only` не создаёт владельцев `frameCache` и `archiveSampler`;
- прямой эфир и архив основного плеера работают в обоих режимах.

## Этап 6. Собрать доказательства baseline и foreground-only

Для каждого запуска использовать один архивный интервал и записать время начала/окончания без URL.

1. Нативный arm64 baseline:
   - эфир;
   - архив на 5–10 минут назад;
   - две минуты непрерывного просмотра;
   - переход назад и вперёд;
   - возврат в эфир.
2. Повторить baseline в x86_64 через Rosetta.
3. Повторить оба запуска с `foreground-only`.
4. Для каждого запуска зафиксировать:
   - скачки только изображения или также времени;
   - время до `playing` и `hasVideo`;
   - RTSP-коды;
   - decoder/VideoToolbox;
   - discontinuity/late frame/RTP-сообщения;
   - максимальное число владельцев и наблюдаемых RTSP-соединений.
5. Проверить лог автоматическим поиском на адрес с user-info, имя пользователя и пароль, не выводя найденные значения. Любое совпадение блокирует дальнейшие эксперименты до исправления redactor.

Решение после этапа:

- скачки исчезли только в `foreground-only` — остановиться и представить отчёт о конкуренции/лимите сеансов;
- скачки сохраняются — перейти к этапу 7;
- результат нестабилен — повторить тот же профиль, не добавляя новую переменную.

## Этап 7. Сравнить входной поток с FFmpeg

Этот этап начинается только если `foreground-only` не помог.

Ограничения среды:

- встроенный universal FFmpeg 8.1.2 собран без видеодекодеров и может использоваться только для transport/remux-диагностики;
- установленный `/usr/local/bin/ffplay` содержит только x86_64 и на Apple Silicon запускается через Rosetta;
- установка или сборка arm64 ffplay требует отдельного согласования, если x86_64-сравнение недостаточно.

Шаги:

1. Остановить MiniCam и убедиться, что его RTSP-сеансы освобождены.
2. Открыть тот же архивный интервал в ffplay по UDP. Учётные данные получает запускаемый Debug-helper из Keychain; команда, пароль и полный URL не журналируются и не отображаются агенту.
3. Собирать очищенный stderr FFmpeg: decoder, PTS/DTS, packet loss, RTP reorder и discontinuity.
4. Если ffplay также скачет, повторить только с TCP.
5. Если ffplay плавный, зафиксировать входной UDP как рабочий и вернуться к экспериментам pipeline VLCKit.

Нельзя использовать remux в локальный поток обратно в VLCKit как результат этого этапа.

## Этап 8. Условные эксперименты VLCKit

Каждый подпункт реализуется отдельным коммитом, запускается против baseline и затем удаляется либо оставляется как подтверждённый кандидат.

### 8.1 Software decoding

1. Добавить профиль `software-decoding`, меняющий только архивный основной плеер.
2. Не менять эфир, transport, cache и frame policy.
3. По VLCKit-логу доказать, что VideoToolbox не выбран и используется software decoder.
4. Повторить двухминутный сценарий и при успехе десятиминутный прогон с измерением CPU.

### 8.2 Политика поздних кадров

1. Вернуть baseline decoder.
2. Добавить профиль `default-frame-policy`, который только для архивного основного плеера убирает `--no-drop-late-frames` и `--no-skip-frames`.
3. Сравнить сообщения late/drop/skip и визуальный результат.

### 8.3 VLCKit 4

1. Выполнить в отдельном варианте зависимостей и сборки, не заменяя VLCKit 3 в основной схеме.
2. Проверить тот же интервал, первый вывод, снимки, callbacks, seek, Intel/Rosetta и macOS 12 deployment target.
3. При положительном результате подготовить отдельный дизайн миграции; не включать alpha в Release автоматически.

## Этап 9. Подготовить диагностический отчёт

Создать `docs/diagnostics/apple-silicon-archive-report.md` и указать:

- таблицу запусков и единственную изменённую переменную;
- слой возникновения проблемы;
- подтверждающие строки уже очищенного журнала без длинных сырых дампов;
- опровергнутые гипотезы;
- рекомендуемое минимальное исправление;
- влияние на эфир, Intel, CPU и число RTSP-сеансов;
- оставшиеся риски.

Закоммитить отчёт отдельно и запросить согласование решения. До согласования не реализовывать исправление и не собирать финальную Universal Release.

## Этап 10. Проверка будущего исправления

После отдельного согласования и реализации причины:

1. Запустить все unit-тесты.
2. Проверить Apple Silicon: десять минут архива без обратного движения изображения, двадцать переходов, соседние сегменты, возврат в эфир, кеш/анализ после переходов и экспорт.
3. Проверить физический Intel Mac тем же сценарием.
4. Собрать Universal Release через workspace с macOS 12 deployment target.
5. Проверить `arm64` и `x86_64` у приложения, VLCKit и FFmpeg.
6. Убедиться, что Debug-аргументы, файлы и logger не активны в Release.
